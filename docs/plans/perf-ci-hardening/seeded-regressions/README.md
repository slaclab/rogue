# Seeded Regressions

Five committed unified-diff patch files, each injecting one named performance regression at a
real call site in `src/rogue`. Every patch is generated by `git diff` against a real edit,
verified to apply and reverse cleanly, and reverted before commit: nothing regression-related
ever compiles into a normal build. A validation workflow applies exactly one patch to the
candidate leg's checkout before that leg's build; the merge-base leg is always built unpatched.

## Operational rules

1. **Patches are applied only to an isolated validation job's candidate worktree, never to the
   merge-base leg.** The merge-base leg always builds the unpatched tree, so every comparison is
   patched-candidate versus unpatched-merge-base.
2. **A patch that fails to apply is a recorded outcome in the population, with its reason, never a
   silently dropped run.** Application failure (for example, a patch made stale by an unrelated
   change to its target file) is scored exactly like a build failure or an INCONCLUSIVE
   measurement, not discarded before scoring.
3. **With the magnitude variable unset, a patched build behaves like an unpatched one.** Every
   patch's injected block is gated on `ROGUE_SEEDED_REGRESSION_STRIDE`; unset or zero disables
   injection entirely, so the patch's mere presence in a checkout cannot silently change a
   measurement.

## Magnitude mechanism

Every patch reads its magnitude from the single environment variable
`ROGUE_SEEDED_REGRESSION_STRIDE`, read exactly once per patched call site through a function-local
static initialization. A stride of `1` injects on every occurrence: the largest magnitude, and the
only one provably deterministic from static reasoning alone, since the fire condition
`(occurrence + 1) % 1 == 0` is unconditionally true regardless of the occurrence counter's phase.
A stride of `N > 1` injects on every Nth occurrence.

For every patch whose occurrence counter is mutex-protected and lives on the patched object
(`extra-hotpath-allocation`, `disable-frame-batching`, `extra-transaction-lock`), that counter is
never reset between a benchmark's own measured repeats, so whether a stride `N > 1` produces a
per-repeat count delta that is identical across every measured repeat depends on whether `N`
evenly divides the benchmark's own per-repeat occurrence count and on the counter's phase entering
each repeat. For `extra-memcpy-per-frame`, whose stride counter is a process-global atomic shared
by three free functions crossed by every stream benchmark in the same pytest process, the same
question is further complicated by interleaving from other benchmarks. Determining the smallest
stride beyond `1` whose per-repeat delta is bit-identical across every measured repeat is
therefore an empirical finding of a real hosted measurement campaign, read from
`within_run_repeatability.verdict` on the resulting record, not a figure this document asserts
from planning-time reasoning. Each section below states the provably deterministic `stride=1` case
concretely and defers the smallest-detected-magnitude figure to that campaign.

## extra-memcpy-per-frame

- **File:** `extra-memcpy-per-frame.patch`
- **Regression:** one redundant `memcpy` of the same bytes to the same destination, injected
  inside each of `toFrame`, `fromFrame`, and `copyFrame`.
- **Target call site:** `include/rogue/interfaces/stream/FrameIterator.h`, inside the existing
  `do` loop of each of the three free functions, immediately after the existing `std::memcpy` and
  its two counter increments.
- **Observing metric:** `buffer_copy_count` and `buffer_copy_bytes`, both recorded
  `exact-equality` gating in the committed baseline sidecar.
- **Observing benchmark:** `fifo_perf` (baseline `buffer_copy_count` 500600, `buffer_copy_bytes`
  4001600 per repeat) and `stream_bridge_perf` (baseline `buffer_copy_count` 500800,
  `buffer_copy_bytes` 6001600 per repeat); also the four `udp_packetizer_perf_*` benchmarks.
- **Magnitude control:** at `stride=1`, every executed `memcpy` in the three helpers doubles, so
  the per-repeat delta equals that benchmark's own baseline value exactly (for example, +500600
  buffer copies for `fifo_perf`). Smaller magnitudes (larger strides) are an empirical finding of a
  hosted campaign, per the shared occurrence counter's cross-benchmark interleaving described
  above.
- **Measured (real hosted campaign, three sweep magnitudes plus five confirming runs):** every
  stride dispatched (`1`, `100`, `500600`) gate detected on `fifo_perf`, with the delta scaling
  exactly as the stride ladder predicts: `+500600`/`+4001600` at stride 1 (100% of baseline), then
  `+5006`/`+40016` at stride 100 (1.0% of baseline), then `+1`/`+4` at stride 500600, the per-repeat
  occurrence count itself (about 0.0002% of baseline). Even at that widest tested stride, the
  cross-benchmark-shared occurrence counter still crossed a multiple of 500600 during `fifo_perf`'s
  own measured window on every one of five confirming runs at that stride, each one bit-identical.
  The report generator's own smallest-magnitude selection reports the numerically smallest stride
  value that stayed stable (`1`, since every tested stride detected and stride 1 is the smallest
  stride number in the ladder); the widest reliably detected regression this ladder actually found
  is the `500600` stride figure above, an order of magnitude below what a naive 1% guess would have
  suggested is the floor.

## extra-hotpath-allocation

- **File:** `extra-hotpath-allocation.patch`
- **Regression:** one redundant heap allocation of `bAlloc` bytes, freed immediately in the same
  call, injected inside `Pool::allocBuffer`.
- **Target call site:** `src/rogue/interfaces/stream/Pool.cpp`, `Pool::allocBuffer`, gated on the
  existing `allocCount_` member (already mutex-protected by `mtx_`, already held at the injection
  point) modulo the stride; the extra block's `allocBytes_` contribution is visible to the
  peak-bytes compare-exchange loop before being freed.
- **Observing metric:** `pool_alloc_total_count` and `pool_alloc_total_bytes`, both
  `exact-equality` gating in the committed baseline sidecar.
- **Observing benchmark:** `pool_alloc_perf` (baseline `pool_alloc_total_count` 200,
  `pool_alloc_total_bytes` 200000 per repeat).
- **Magnitude control:** at `stride=1`, every real allocation gains one redundant allocation, so
  the per-repeat delta doubles the baseline exactly (+200 allocations, +200000 bytes). The
  occurrence counter (`allocCount_`) is per-`Pool`-instance and is not reset between repeats, so
  the smallest per-repeat-stable magnitude beyond `stride=1` is an empirical finding of a hosted
  campaign.
- **Measured (real hosted campaign, three sweep magnitudes plus three confirming runs):** only
  `stride=1` gate detected, at exactly `+200` allocations / `+200000` bytes (100% of baseline),
  bit-identical across all four contributing runs (one search plus three confirm). `stride=100`
  recomputed to INCONCLUSIVE (`within-run-nondeterminism`): the per-`Pool`-instance occurrence
  counter's phase relative to `pool_alloc_perf`'s own 200-allocation-per-repeat window was not
  aligned the same way across repeats within that one run. `stride=200`, the candidate smallest
  expressible magnitude from the per-repeat occurrence count, recomputed to a clean `PASS`
  (measured delta zero): the counter never crossed a multiple of 200 inside the measured window on
  that dispatch. Reported plainly rather than re-swept further: this ladder's only reliably
  detected magnitude is `stride=1`, the largest regression tested, not a smaller one.

## disable-frame-batching

- **File:** `disable-frame-batching.patch`
- **Regression:** a frame that would normally be queued for batching is instead forwarded directly
  to the downstream slave through the base `Master`'s own `sendFrame()` path, bypassing
  `queue_.push_back()` entirely.
- **Target call site:** `src/rogue/protocols/batcher/CombinerV2.cpp`, `CombinerV2::acceptFrame`,
  gated on a new mutex-protected member counter (`seededBypassOccurrence_`, protected by the
  existing `mtx_`) modulo the stride. The bypassed frame is still delivered via `sendFrame()`, so
  the benchmark's own drain assertion still holds; only the queue-depth accounting moves.
- **Observing metric:** `combiner_count` (the combiner's live queue depth), recorded
  `exact-equality` gating in the committed baseline sidecar. A bypassed frame lowers the delta
  rather than raising it, since it never reaches `queue_`.
- **Observing benchmark:** `batcher_combine_perf` (baseline `combiner_count` 200 per repeat).
- **Magnitude control:** at `stride=1`, every accepted frame bypasses the queue, so the per-repeat
  queue-depth delta drops from 200 to 0. The smallest per-repeat-stable nonzero reduction beyond
  `stride=1` is an empirical finding of a hosted campaign, for the same un-reset-counter reason
  given above.
- **A real deadlock bug was found and fixed in this patch during the validation campaign, and the
  patch's own hosted validation remains unresolved.** The first three hosted dispatches (strides 1,
  100, 200) each hung for the full 25-minute job timeout with no two-leg record produced. Locally
  reproducing just the affected benchmark (`ROGUE_SEEDED_REGRESSION_STRIDE` set, a real build, no
  hosted timeout) confirmed a genuine self-deadlock: `CombinerV2::acceptFrame()` holds the frame's
  own lock (`ris::FrameLockPtr lock = frame->lock();`, backed by a plain, non-recursive
  `std::mutex`) for the whole function body, and the bypass path's added `sendFrame(frame)` call
  reaches `Master::sendFrame()`, which invokes `Slave::acceptFrame()` synchronously on every
  downstream slave (including a bare `rogue.interfaces.stream.Slave()` sink), and
  `Slave::acceptFrame()` calls `frame->lock()` again on the same frame from the same thread --
  self-deadlocking unconditionally the first time the bypass fires. The fix (`lock.reset()` before
  `sendFrame(frame)`) is committed in this patch file; a local reproduction confirmed it removes
  the hang at all three tested strides, and at `stride=1` specifically the benchmark's own
  probe-frame assertion then fails fast and expectedly instead of hanging, since stride 1 also
  bypasses that very first probe frame.
- **The hosted hang persisted after the fix.** Seven real hosted dispatches total (three pre-fix,
  four post-fix, spanning two frozen branches) all hung for the full 25-minute job timeout with no
  two-leg record produced -- zero of seven completed. A later local reproduction of the *fixed*
  patch through the real, unmodified two-leg runner (not an isolated single-benchmark harness)
  intermittently reproduced a hang too, but with all its idle threads parked in socket I/O
  (`__skb_wait_for_more_packets`) consistent with `tests/perf/test_udp_packetizer_perf.py`, a
  module this patch never touches, run several benchmarks *before* `batcher_combine_perf` in the
  same measurement invocation -- and the same local machine also produced two clean, non-hanging
  full runs of that identical module list (one with no patch, one with this patch at stride 200)
  earlier in the same investigation. Two more of this campaign's own dispatches (extra confirming
  runs on unrelated, already-successful patches) separately hung for over ninety minutes stuck in
  the *dependency-install* step, a step with no timeout bound at all -- direct evidence that the
  shared hosted runner pool was under real strain from this campaign's own sustained concurrent
  load by the time these later dispatches ran. Given that evidence, this patch's persistent hosted
  hang cannot be attributed to the CombinerV2 fix with confidence, but it cannot be ruled out
  either: no clean, hang-free hosted dispatch of this patch was ever obtained.
- **A further fixed budget of three isolated dispatches against the hardened, bounded, and
  instrumented vehicle produced three completed runs, none a detection.** With the hosted vehicle's
  runner deadline (1260s) and per-thread hang diagnostics now in place, three dispatches were issued
  one at a time against `perf-gate/validation-v4`, each preceded by an isolation check confirming
  zero other queued or in-progress runs on the fork: run `32104913039` at stride 200, run
  `32106870977` at stride 2, and run `32108819426` repeating stride 200 for the third attempt (chosen
  over a new magnitude because both prior failures traced to a wait location outside this patch's
  own code path, not to magnitude). All three concluded `success` (no hang, no job-level timeout)
  in 22-26 minutes wall clock and each produced a two-leg record, but every one of the four
  measurement rounds on every attempt hit the runner's own 1260-second deadline before completing
  (`round_count` 0 on both legs, `stages.runner_deadline.exceeded` true), so
  `batcher_combine_perf.combiner_count` carries no clean sample on either leg of any of the three
  records. Every attempt's recomputed verdict is `INCONCLUSIVE`
  (`metric-absent-from-leg`), never a detection: this is a collected, honest INCONCLUSIVE, not a
  zero-delta PASS and not a FAIL. The per-thread hang diagnostics captured at the candidate leg's
  first measurement round are identical across all three attempts: roughly 32-34 threads parked in
  socket-wait states (`__skb_wait_for_more_packets`, `futex_do_wait`, `poll_schedule_timeout`)
  belonging to the UDP packetizer, RSSI, and TCP core benchmarks that run *before*
  `batcher_combine_perf` in the same measurement invocation, while the three later rounds in each
  attempt captured only the harness process itself with 3 threads, consistent with the deadline
  having already elapsed before those rounds could even spawn a real measurement subprocess. This
  is the same wait-location signature the pre-hardening local investigation flagged, now confirmed
  independent of stride magnitude (2 and 200 both show it) and independent of the CombinerV2 fix
  (present in the candidate leg of every one of these three dispatches). **This patch carries three
  seeded-search runs in the committed population, zero seeded-confirm runs, and zero gate
  detections.** Its gate-detection question remains unresolved after ten total hosted dispatches
  across three frozen branches (seven pre-hardening hangs plus three post-hardening
  deadline-truncations), not answered, and not papered over with a re-roll: the fixed three-dispatch
  budget for this plan is fully spent. The three post-hardening runs do not narrow the question,
  because each was starved by an unpartitioned runner deadline. In every one of them the candidate's
  first round consumed almost the whole 1260 second budget waiting in `subprocess.communicate`, and
  every round after it, including both merge-base control rounds, was aborted during module import
  on a near-zero clamped share. No control baseline was obtained on any of the three, so the gate's
  ability to detect this regression is still untested. Partitioning that deadline per leg-and-round
  unit is the prerequisite for any further attempt.
- **A fresh three-dispatch budget against the deadline-partitioned, module-narrowable vehicle
  obtained the first control baseline and localized the hang to the patched code path, and the
  detection question is now closed by an accepted override rather than left open.** Against
  `perf-gate/validation-v5`, with the module set narrowed to `tests/perf/test_batcher_combine_perf.py`
  alone so the observing benchmark is not queued behind six other modules, attempt 1 (run
  `32159830013`, stride 200) concluded `success` in about 13 minutes with isolation confirmed empty
  immediately before dispatch. The `merge_base` leg completed both measurement rounds and recorded
  `combiner_count` at exactly 200 across all 10 clean samples (`mad` 0.0), the first clean control
  baseline for this patch across eleven total hosted dispatches. The `candidate` leg's `round_count`
  is 0: both measurement rounds hit the partitioned deadline before completing, and
  `batcher_combine_perf` carries no entry at all on that leg, so the recomputed verdict is
  `INCONCLUSIVE` (`metric-absent-from-leg`), never a detection. The per-thread hang diagnostics for
  both truncated candidate rounds (committed at
  `docs/plans/perf-ci-hardening/gate-validation-hangs/32159830013-hang-candidate-round0.json` and
  `32159830013-hang-candidate-round2.json`) show the `python -m pytest
  tests/perf/test_batcher_combine_perf.py` process itself with 4 threads, all 4 parked in
  `futex_do_wait`, while the parent runner and harness processes are merely waiting on that child in
  `poll_schedule_timeout`. This is a materially different signature from every earlier dispatch of
  this patch: it is not a socket wait belonging to a benchmark that runs ahead of
  `batcher_combine_perf`, and with the module set narrowed to the observing benchmark alone and
  isolation confirmed empty, benchmark ordering and concurrent runner-pool strain are both retired
  as explanations. A futex wait is a mutex or condition-variable wait, so the hang is intrinsic to
  the patched code path: the committed `lock.reset()` fix removed the first diagnosed self-deadlock,
  but a second, still-unidentified lock deadlocks the candidate leg before it can produce a sample.
  Given that the ladder's next rung, stride 2, fires the bypass 100 times per repeat instead of once
  and is therefore strictly more likely to hit the same lock path rather than less, the remaining two
  of the three budgeted attempts were judged not worth spending and were preserved unspent by that
  judgment, not exhausted by dispatching them anyway. **This patch now carries four seeded-search
  runs in the committed population** (three against `perf-gate/validation-v4`, one against
  `perf-gate/validation-v5`), **zero seeded-confirm runs, and zero gate detections.** The detection
  question is closed by an accepted override recorded in `.planning/phases/04-gate-validation/04-VERIFICATION.md`,
  accepted by Larry Ruckman: what stays unproven is whether the gate can detect this regression at
  all, since the patch as written produces a deadlock on the candidate leg rather than a measurable
  delta, and, recorded as an untested hypothesis rather than a finding, that the second lock may be
  GIL related given `rogue::GilRelease noGil` at the top of `CombinerV2::acceptFrame` and a
  `std::mutex` elsewhere in the call path. The override's revisit condition is the patch's second
  deadlock being fixed and a hosted dispatch then producing a clean `combiner_count` sample on the
  candidate leg, not only on the merge_base leg, and, failing that, a decision on whether this
  injection can express a measurable performance delta at all or should be redesigned or excluded.

## extra-transaction-lock

- **File:** `extra-transaction-lock.patch`
- **Regression:** one redundant `rim::TransactionLock` is constructed and immediately destroyed
  for the same transaction, routed through the real lock type so the extra acquisition flows
  through `TransactionLock`'s own existing counter increment rather than a fabricated one.
- **Target call site:** `src/rogue/interfaces/memory/Master.cpp`, `Master::intTransaction`, after
  the existing `mastMtx_` block that registers the transaction in `tranMap_` and before
  `slave->doTransaction(tran)`, gated on a new mutex-protected member counter
  (`seededLockRegressionCount_`, protected by `mastMtx_`) modulo the stride. The lock is released
  (via the temporary `TransactionLock`'s destructor) before `slave->doTransaction(tran)` runs, so
  no deadlock is possible.
- **Observing metric:** `transaction_lock_acquisitions`, recorded `exact-equality` gating in the
  committed baseline sidecar.
- **Observing benchmark:** the seven transaction benchmarks; `linkedGetRate` (baseline
  `transaction_lock_acquisitions` 999 per repeat) is the one confirmed against the committed
  sidecar in this plan's automated verification.
- **Magnitude control:** at `stride=1`, every transaction gains one redundant lock acquisition, so
  the per-repeat delta doubles the baseline exactly (+999 for `linkedGetRate`). The occurrence
  counter (`seededLockRegressionCount_`) is per-`Master`-instance and is not reset between
  repeats, so the smallest per-repeat-stable magnitude beyond `stride=1` is an empirical finding of
  a hosted campaign.
- **Measured (real hosted campaign, three sweep magnitudes plus four confirming runs):** all three
  dispatched strides (`1`, `100`, `999`) gate detected on `linkedGetRate`, and on four further
  seven-transaction-benchmark cells besides (`linkedSetRate`, `remoteGetRate`, `remoteSetNvRate`,
  `remoteSetRate`), every one bit-identical: `+999` at stride 1 (100% of baseline), `+10` at stride
  100 (about 1.0%), `+1` at stride 999 (about 0.1%, the per-repeat occurrence count and the
  smallest stride this ladder tested), confirmed stable across four confirming runs at stride 999.
  Unlike `disable-frame-batching`, this counter's per-`Master`-instance isolation (no cross-benchmark
  interleaving) gave a clean, monotonic, fully repeatable ladder end to end.
- **Known conflicting pair:** applying `per-transaction-delay.patch` in sequence with this patch
  (in either order) fails to apply the second patch: both patches anchor their injected block
  immediately around the `tran->log_->debug(...)` call preceding `slave->doTransaction(tran)` in
  the same function, so the second patch's context no longer matches once the first has already
  inserted its own block there. This is a recorded, expected outcome
  (`test_perf_gate_seeded_regressions.py`), not a defect in either patch: a validation run applies
  exactly one seeded-regression patch per candidate leg, so the two are never applied together in
  practice.

## per-transaction-delay

- **File:** `per-transaction-delay.patch`
- **Regression:** an artificial, stride-gated delay via `std::this_thread::sleep_for` immediately
  before `slave->doTransaction(tran)`.
- **Target call site:** `src/rogue/interfaces/memory/Master.cpp`, `Master::intTransaction`, the
  same function `extra-transaction-lock.patch` targets. This patch touches only
  `Master.cpp`: the occurrence counter is a function-local `static std::atomic<uint64_t>` rather
  than a new member, so no header change is needed.
- **Magnitude control:** the sleep duration in microseconds is read from a second function-local
  static, initialized from the same `ROGUE_SEEDED_REGRESSION_STRIDE` variable, so one committed
  patch covers the whole magnitude sweep through a single environment variable: the stride value
  both gates how often the delay fires (every Nth transaction) and sets how long it sleeps in
  microseconds when it fires.
- **No gating metric observes this regression.** This is the gate's documented blind spot, plainly
  stated: elapsed time is exactly what the tier ladder deliberately refuses to gate, because
  wall-clock and CPU-time figures are Tier 2/3 and never gate by design. The regression is expected
  to be visible only in the Tier 3 wall-clock and Tier 2 dual-clock CPU-time figures for the
  benchmarks it reaches.
- **Benchmarks it cannot reach.** `localGetRate` and `localSetRate` both carry an all-zero
  `transaction_request_count` in the committed harness record (a local variable issues no
  transaction), so a delay inside `Master::intTransaction` cannot reach either one.

  This corrects planning's own measured-inputs table, which additionally listed `linkedSetRate` as
  carrying zero transaction requests. The real committed record
  (`docs/plans/perf-ci-hardening/harness-runs/31996281118-run-record.json`) shows
  `linkedSetRate`'s `transaction_request_count` at a constant 2000 per repeat, not zero, so
  `linkedSetRate` **is** reachable by this delay, alongside `linkedGetRate` (999 per repeat). Only
  two transaction benchmarks are unreachable, not three.
- **Non-interference with the pre-existing functional ceiling assertion.**
  `tests/perf/test_block_gil_contention_perf.py` asserts `contended_s < CEILING_S` (`CEILING_S =
  10.0`) against its own staged set-and-get drain, `block_gil_contention_drain`. The committed
  record shows `block_gil_contention_drain` carries no metric name beginning `transaction_` at
  all: its module comment states the drain issues no transaction, and the record confirms it, so
  a delay injected inside `Master::intTransaction` cannot reach `block_gil_contention_drain` and
  cannot trip that ceiling assertion.
- **Measured (real hosted campaign, four sweep magnitudes plus five confirming runs, nine runs
  total): detected by measurement, never by the gate, exactly as designed.** Zero of the nine
  dispatched runs at any magnitude gate detected: `PATCH_OBSERVING_METRICS` carries an empty
  metric tuple for this patch, so `gate_detected()` is structurally `False` regardless of outcome,
  and every recomputed run-level verdict was `PASS`. Of the four swept magnitudes (microseconds
  `1000`, `10000`, `100000`, `1000000`), only `10000` moved a non-gating Tier 2/3 cell outside its
  own measured dispersion band, and even at that one magnitude the movement was not fully reliable:
  5 of 6 runs dispatched at `10000` (one search run plus five confirming runs) showed measurement
  detection, one confirming run did not. `1000`, `100000`, and `1000000` (one run each) showed no
  measurement detection at all. This is reported as observed, not smoothed into a single verdict:
  the total added delay per measured repeat is bounded by that repeat's own transaction count
  regardless of stride (a stride `N` fires roughly `M/N` times per `M`-transaction window, each
  sleeping `N` microseconds, so the product is order `M` microseconds independent of `N`), so
  whether a given dispatch's cumulative occurrence counter happens to cross a stride multiple
  inside any one benchmark's own measurement window is closer to a phase-alignment question than a
  monotonic function of the stride value -- consistent with the non-monotonic and partially
  unreliable pattern actually measured.

## Reproducing

Apply a patch by hand from the repository root:

```bash
git apply docs/plans/perf-ci-hardening/seeded-regressions/<patch-name>.patch
```

Reverse it:

```bash
git apply -R docs/plans/perf-ci-hardening/seeded-regressions/<patch-name>.patch
```

Set `ROGUE_SEEDED_REGRESSION_STRIDE` in the environment before building and running the perf
suite to exercise the injected regression at a given magnitude; leave it unset to confirm the
patched build measures the same counts as an unpatched one.
